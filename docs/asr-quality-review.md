# 识别质量排查与平衡方案

2026-10-28。用户确认本次是英语课，错误发生在识别原文。当前设置为英语、Whisper Large v3 Turbo、CUDA INT8/FP16、识别 beam 3；这些识别参数没有因之前的性能调优降档。翻译 beam 2 → 1 不影响已经输出的英文识别原文。

## 采样前排查的边界（历史记录）

- 语音先经过 WebRTC VAD mode 2 分段，再经过 faster-whisper 内的 Silero VAD。重复过滤确实存在，但未拿到本次课程的声音，不能认定它就是本次错误原因。
- 连续讲话最长约 5 秒强制切段，段间没有重叠音频，也没有显式传递上一段文本；切在单词或长句中间时，语境可能不足。把 `condition_on_previous_text` 改成 True 仅影响一次调用内部，不能自动跨这些独立调用传递上下文。
- 多声道音频直接平均；普通立体声可用，但特殊反相音轨可能抵消。尚无证据说明本课存在这一情况。
- 日志没有本课原始音频或逐段识别质量记录；界面丢帧 / 跳段计数也不能当成词错误率。

上游依据：[faster-whisper v1.2.1 解码、提示与上下文实现](https://github.com/SYSTRAN/faster-whisper/blob/v1.2.1/faster_whisper/transcribe.py)、[同版本 VAD 实现](https://github.com/SYSTRAN/faster-whisper/blob/v1.2.1/faster_whisper/vad.py)。

## 本次轻量诊断

使用项目已有的合成英语 9.868 秒和德语短样本，分别保留原音量、降低 24 dB、降低 36 dB，共 6 组。没有打开声卡，也没有加载 Whisper 权重。

英语外层 VAD 保留的时长从 8.56 秒变为 8.30 / 8.12 秒；德语从 1.70 秒变为 1.58 / 1.48 秒。时长变短不能直接解释为丢词，因为其中可能是静音边沿。所有这 6 组中，内层 Silero 都没有继续删除外层已经保留的样本。该结果不支持无条件关闭内层 VAD，也不能用来说明嘈杂教室、口音和低信噪比音频都没有问题。原始结果见 [VAD 保留记录](validation-vad-quality.json)。这是保留时长测试，不是识别准确率测试。

当时系统可用 RAM 约 0.88 GiB，因此没有在正在使用的环境里额外加载另一套 Whisper 做速度测试。不能据此报告新识别配置的词错误率、延迟或显存峰值。

## 最初的比较计划（历史记录）

| 方案 | 预期作用 | 资源与行为取舍 |
| --- | --- | --- |
| 视频课优先系统回环；确认电平、削波和输入来源 | 减少扬声器到麦克风的二次收音；定位原始输入问题 | 基本无需额外推理资源；现场课程仍取决于麦克风和距离 |
| 增加少量课程术语提示 | 针对专业词、缩写、人名的错误 | 不加载新模型，提示过长或不相关也可能诱导错误；需同音频比较 |
| 课堂均衡档：切段上限 5 → 7 秒，停顿 0.5 → 0.65 秒，保持 beam 3 | 争取更自然的词 / 句边界与上下文 | 连续讲话可能多等约 2 秒；音频缓冲增加很小，整体处理速度和解码显存仍需实测 |
| 用本课素材对照 VAD 灵敏度与单层过滤 | 检验弱音是否在进模型前被截掉 | 更宽松会让更多噪声进入识别，也可能增加幻觉，不能只凭时长保留率判断 |
| 最后对照 beam 3 / 5，或有预算时仅对疑难段重试一次 | 检查候选搜索是否能改善错词 | 增加解码耗时与临时显存；不能恢复已经丢失的声音，低置信度分数也不等于校准后的准确率 |

优先保留 Turbo、当前量化和 beam 3。暂不默认换大模型、全 FP16、跨段无限上下文或额外神经降噪。简单放大音量并不改善信噪比。faster-whisper 的 log-Mel 处理也不是波形自动增益，见 [特征提取实现](https://github.com/SYSTRAN/faster-whisper/blob/v1.2.1/faster_whisper/feature_extractor.py)。

## 下一步用同一段课堂声音验证

增加了手动的最多 5 分钟诊断采样，正常同传仍不保存录音。保存进入 VAD 前的 16kHz 单声道识别输入、当前已完成的原文、课程时间和参数；不额外加载识别模型、不自动上传。使用方法见 README 的“采集识别诊断素材”。

比较时用同一素材与几处人工确认的错词，分别检查漏词、错词、字幕分段、处理时长与资源余量。最好同时包含出错片段和正常片段。数据到手前不宣称某个参数能保证改善本次课程。

## 本课采样后的结果

用户已提供约 5 分钟现场麦克风素材，并确认涉及随机变量与 Markov property。离线实测保持同一 Turbo 模型：单纯关闭内层 VAD 耗时增加，7 秒自然断句的识别效果有改善也有退化，beam 3 → 5 在相同 11 个窗口增加约 14.8% 计算，未显示稳定术语收益。这些设置没有改成默认。

少量用户确认的课程术语提示，在部分同片段中将 `stochastic posts` 改为 `stochastic processes`、`Brendan Barrett` 改为 `random variables`；但仍有 Markov property、X / Y 等错误。没有完整人工参考，因此不报告准确率提高百分比。完整参数、候选文本和耗时保留在该素材目录的 `comparison-review.md` 与 JSON 中，不纳入源码发布。

用户进一步指出，专业术语本来较好，普通描述语句才是主要问题。此前增加的可选课程术语已撤回，不再出现在设置、配置或 CLI 中；这次转向描述句的上下文与切分。

## 10 月 28 日描述句对照（历史选择）

现有素材足以测试切分，不要求再次录制。保持同一 Turbo、CUDA INT8-FP16、beam 3、两层 VAD 与预卷参数，分别比较原 94 个事件、向前拼接 3 秒原音频后按词时间戳裁剪、以及 8 秒上限 / 0.8 秒停顿的完整重分段。三轮均无术语提示，使用一套复用的模型，进程完成后已释放。

3 秒回看耗时从 18.31 秒增加到 39.08 秒，并出现词时间戳分配到旧区间、裁剪后当前段为空的问题，未实施。8 秒 / 0.8 秒产生 56 个片段，耗时 21.75 秒，几处普通描述的候选更连贯；原事件缺少末尾待推理尾段，新分段额外覆盖约 2.3 秒，耗时不是严格同输出范围的速度比。没有逐字人工参考，不能给准确率提升比例，较长分段仍有错词。

应用默认改为“连贯优先”：最多 8 秒、停顿 0.8 秒；设置中的“低延迟”恢复原来 5 秒 / 0.5 秒。没有增加模型、候选数、词时间戳、重识别或跨段文本提示。主要代价是短停顿多等约 0.3 秒，连续讲话最多多等 3 秒，再加推理时间。单段 16kHz float32 波形的容量上限从 320,000 字节变为 512,000 字节；这不代表神经推理峰值内存，也不是 90 分钟功耗保证。

两档均验证 90 分钟加速流、暂停 / 继续、停止尾句、队列界限、偏好持久化与诊断参数记录。包含课堂文字的详细对照位于被忽略的素材目录 `comparison-description-review.md`，不会随源码公开。

## 10 月 29 日：收音较好时的实时等待

新素材完整 300 秒。排除起点前片段后，成功字幕 49 条的识别耗时中位约 0.735 秒、翻译 0.360 秒、合计 1.094 秒，记录中排队、采集丢帧与跳段均为 0。主要等待来自收集当前语音段；英文与中文在翻译后一起显示，不能据此单独判断识别慢。

保持相同模型、量化、beam 3 和双层 VAD，比较固定短分段与自然停顿。固定 6 秒 / 0.6 秒产生更多短段，部分描述变化较大，没有设为默认。严格保留约 4.5 秒上下文后，才允许 0.3 秒停顿提前处理：短句仍使用 0.8 秒、连续讲话仍最多 8 秒。按用户最后要求，清晰档最终仅依据本次素材选择：4 秒只比 4.5 秒平均再省约 0.15 秒，却使本次企业文化、HR 职能等描述进一步破碎，计算耗时也较高，因此保留 4.5 秒。

同一完整 WAV、一套复用的 ASR + MT 模型的离线串行回放，按 VAD 有声帧估计首批可见字幕等待：原模式平均 4.41 秒 / P90 7.77 秒，4.5 秒候选平均 3.87 秒 / P90 6.63 秒。总 ASR + MT 计算耗时约 39.97 → 40.79 秒，单轮仅小幅增加，不构成通用功耗或性能保证。模型没有更换、没有增加候选、重识别、批量或第二套常驻模型。该等待估计不含声卡、采集队列或界面绘制，且覆盖的是 VAD 帧而非人工对齐的单词。

最终按场景提供默认“清晰收音（实时优先）”、保留原参数的“较差收音（长上下文）”及“低延迟”。清晰档仅针对本次录音优化，不以旧录音牵制参数；较差收音本轮不继续调参，留待后续专门素材。个别句子仍有遗漏或措辞变化，不能承诺准确率完全不变；原有明确偏好不被强行迁移。无完整人工参考，不给词错误率。原始录音、候选文字、实际耗时、虚拟时间轴与风险例子均在新素材目录的私有比较报告内。

最初额外模型测试触及可用内存保护后主动中断并释放；在用户结束并释放原同传模型后，最终单套模型流水线对照完成。此前被中断的部分结果保留并标记，未冒充完整测试，也不解释为同传软件模型崩溃。正常运行只保留最新指标与固定大小队列，三档通过 90 分钟加速分段验证，尚无真实硬件 90 分钟温控与峰值内存保证。
