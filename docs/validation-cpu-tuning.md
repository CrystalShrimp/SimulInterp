# 翻译 CPU 线程对照

2026-10-28，在本机 i9-13900HX 上运行本地 M2M100 INT8 翻译。六条自行编写的德语 / 英语课堂句子混合长短，翻译 beam=1、`return_scores=False`，每次只加载一个 CPU 模型，不加载语音模型或创建 CUDA 上下文。每个配置加载、预热后测量相同语料，并清除应用翻译缓存以确保真的推理。两轮顺序为 4→6→8、8→6→4。

| 线程 | 首轮语料耗时 | 第二轮语料耗时 | 用于比较的中值 | 平均整机 CPU |
| --- | --- | --- | --- | --- |
| 4 | 2.824 秒 | 641.921 秒，异常已复核排除 | 2.824 秒，仅一个有效样本 | 正常轮约 12.3% |
| 6 | 2.324 秒 | 2.252 秒 | 2.288 秒 | 约 18.5% |
| 8 | 2.038 秒 | 1.970 秒 | 2.004 秒 | 约 24.0–24.7% |

8 线程比 6 线程的语料中值耗时少约 **12.4%**，CPU 占用更高。应用采用 8 线程作为本机默认值，设置仍可选择 6 线程以减少 CPU 负载，或 4 线程进一步减少参与的核心数。这里没有测试 90 分钟的功耗、风扇或温控表现，也没有证明线程增加可明显节省常驻内存。

加载后采样到进程工作集约 646–651 MiB；三种线程配置差异很小。这是该 CPU 基准进程的采样值，不是保证峰值，也不代表完整语音识别应用的内存占用。CPU 百分比按 32 个逻辑处理器的整机容量归一化，未包含其他程序负载。

第二轮 4 线程出现长时间低 CPU 停顿：六句中两句耗时约 16.627 / 623.503 秒。该轮结束时采样可用内存约 263 MiB；此前正常配置约为 615–821 MiB。现有数据无法断定停顿来自换页、调度、系统暂停或其他因素，不能据此宣称“4 线程会卡住”。原始数据和翻译文本完整保留在 [JSON 报告](validation-cpu-tuning.json)，该轮带明确的人工复核排除标记。仅保留一轮有效 4 线程数据，没有再次加载模型补跑。

基准工具现加入加载前至少 1 GiB、加载后及每句开始前至少 512 MiB 的可用内存检查，低于门槛会结束本次基准并释放模型。不可读取的内存值仍保留为未知。长时间低 CPU 停顿会要求人工复核，不会自动删除所有慢样本。门槛只作用于手动基准，不会中断正在进行的课程同传。

可在不进行课程同传时手动重跑：

```powershell
.\.venv\Scripts\python.exe -m simulinterp.benchmark_translation --output cpu-tuning.json
```

CPU 线程与低 beam 翻译的取舍参考 [CTranslate2 官方性能指南](https://opennmt.net/CTranslate2/performance.html)。以上速度来自本机短语料实测，不套用上游硬件数字。
